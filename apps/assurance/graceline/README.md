# Graceline — policy exception and remediation lifecycle

**Educational prototype. Synthetic records only. The policy parameters are a custom rule set, not a published standard.**

Graceline keeps risk-accepted policy exceptions from quietly disappearing. A request moves through a guarded state machine — draft → submitted → under review → active → (expiring) → expired → escalated, or closed / rejected / withdrawn — and every transition is checked against an explicit policy: maximum duration by risk level, compensating controls for high/critical risk, approval quorum with required roles, separation of duties (the requester and the risk owner can never approve), a renewal cap, a grace window before escalation, and closure that needs evidence. Refused actions list every violated rule. Time is a first-class input: set the board date and the engine applies expiry and escalation deterministically.

## Key workflows

1. **Lifecycle board** — five columns with a time ribbon on every card (start → expiry, marker at the board date), quorum progress on cards under review, and a "policy violation on record" flag when an existing record breaks the current policy.
2. **Request detail** — editable while draft; afterwards a read-only record with justification, compensating controls, remediation plan, closure evidence and the full **decision history** (append-only, including system ticks).
3. **Act** — submit, start review, approve (role-tagged), reject (note required), withdraw, request renewal (requester or risk owner only; approvals reset; the current term keeps running until the renewal quorum approves; capped), update remediation, close with evidence.
4. **Attention order** — every open item ranked by `risk weight × state factor × compensating relief + overdue days / 15`.
5. **Board date** — move time forward to watch active items expire and escalate; the notice names each moved record.
6. **Import / export** the board (`graceline.board/1`) or a risk-register export with the ranked list and the policy snapshot.

## Policy (custom educational rule set — see `src/engine/policy.ts`)

| Rule | Value |
|---|---|
| Max duration (start → expiry) | critical 30 d · high 90 d · moderate 180 d · low 365 d |
| Compensating control required | high, critical |
| Approval quorum | low 1 (any role) · moderate 1 (any role) · high 2 incl. **risk-owner** · critical 2: **risk-owner + ciso** |
| Separation of duties | approver ≠ requester and ≠ risk owner; one approval per person |
| Submission | requester only; justification ≥ 30 chars; owner set; remediation plan with due date ≤ expiry; expiry > start |
| Renewal | requested by the requester or the risk owner only, from active or expired, one pending at a time; ≤ 2 *approved* renewals; new expiry ≤ current expiry + max duration and after today. The request resets approvals and records `pendingRenewal`; the record keeps its state and expiry, so it can still expire and escalate and stays overdue. When the quorum approves (same SoD rules), the new expiry applies and the counter increments; refusing the renewal clears it and leaves the current term unchanged. |
| Roles | approver roles are self-asserted names; there is no directory or authentication, so the quorum demonstrates the policy logic, not identity assurance. |
| Time | active → expired the day after expiry; expired → escalated after a 14-day grace window; expiring = within 14 days of expiry |
| Closure | from active/expired/escalated; evidence ≥ 20 chars; remediation marked done |
| Terminal | closed, rejected, withdrawn (withdraw only before activation) |

Known limits: no notifications beyond in-app state; no delegated approvals or approval expiry; no attachment of evidence files (text only); re-rating risk after approval is allowed in imported data and surfaces as a live guardrail violation rather than being blocked.

## Architecture

```
src/engine/policy.ts     policy constants and note
src/engine/lifecycle.ts  applyEvent (guarded transitions), tick (time), derive, prioritise, contentGuardrails
src/engine/validate.ts   bounded import validation (1 MiB, 300 exceptions)
src/ui/*                 React 19: App, Kanban (ribbons), Detail (actions + decision history)
src/fixtures/            12 synthetic exceptions generated by replaying real events (qa/make-fixture.ts via vite-node)
tests/engine.test.ts     27 tests
```

Memory-only state; hash deep links (`#/EX-107`); self-hosted Manrope + Newsreader (OFL-1.1); hardened `vercel.json`.

## Tests

Policy monotonicity; every submission guardrail (duration, compensating, justification, owner, remediation plan/date, requester, expiry > start); quorum for all four risk levels including role requirements; separation of duties and duplicate approvers; rejection/withdrawal rules; tick transitions at exact boundaries, idempotence and non-interference with terminal states; expiring/overdue derivation; renewal reset, cap and bounds; closure evidence; history append-only and input immutability; prioritisation order and compensating relief; live guardrails on imported records; validation paths and bounds; fixture state coverage.

## Data handling

Fictional policies, people and systems. No network or storage APIs; exports via transient Blob URLs.

## JD evidence (truthful framing)

GRC workflow design (risk acceptance, compensating controls, approval governance, remediation tracking), competing-priority triage, and auditable decision history. Not a claim of ServiceNow/Archer workflow experience or of operating a real exception process.
